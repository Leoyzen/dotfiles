# 下属周报撰写指南

本文件是下属撰写周报的模板和原则。可以直接分享给团队成员，帮助他们写出对齐管理者期望的周报。

---

## 为什么要写好周报

周报不是"汇报我做了什么"，而是"让管理者看清进展和风险"。

你的周报会被翻译成面向高管的结构化报告。如果你写得好，管理者可以直接引用；如果你写得不好，管理者需要额外补充和纠正——这会消耗他大量时间。

**写好周报 = 减少管理者的补充工作量 = 你的工作更容易被看见和认可。**

---

## 核心原则

### 0. 先写产品结论

管理者首先要知道：目标是什么、做到哪一步、用户何时能用。技术实现是证据，不是开头。

每项工作先用一句话回答：

```text
[产品目标]已经[阶段结果]，目前[上线/测试/POC/阻塞]，距离[下一里程碑]还差[一项关键事项]。
```

### 1. 先说结论，再说过程

```
❌ "本周做了A，然后做了B，还做了C，其中A遇到一个问题..."
✅ "本周核心进展：[X模块进入验证阶段]。具体：完成了A/B/C三项工作，其中A遇到[问题]，已[处理方式]。"
```

### 2. 关联业务目标，不要只说技术动作

```
❌ "完成Agent Pool迁移"
✅ "完成Agent Pool迁移，支撑630诊断通过率目标，下一步进入动态策略验证"

❌ "SFT Loss从2.946降至0.878"
✅ "AgenticRL训练链路工程化贯通（Loss降低70%），模型自我进化能力初步验证，距业务可用约1-2个月"
```

每项工作都要回答：**这让项目离目标近了多少？**

### 3. 技术细节附带业务翻译

技术细节可以写，但必须附带一句话说明业务意义：

```
❌ "修复了request_comment重试机制，处理了文件夹找不到/LLM路径解析幻觉/JSON缺失等异常"
✅ "标注平台稳定性强化（修复重试机制/异常处理等），平台正式通过业务专家验收"
```

### 4. 主动暴露风险，不要隐瞒

```
❌ "进展顺利，一切正常"
✅ "本周核心进展是X，但存在一个风险：[具体风险]，可能影响[具体影响]，建议[应对方案]"
```

隐瞒风险是最严重的问题。主动暴露问题不会减分，反而会加分——说明你有风险意识。

### 5. 数据要具体，不要模糊

```
❌ "做了一些优化"
✅ "问答准确率从62.15%提升至65.25%（+3.1pp）"

❌ "修复了若干bug"
✅ "修复3个P1级bug（列表），稳定性达到可上线标准"
```

## 周报模板

### 标准格式

```markdown
## @[你的名字] - [日期]

### 本周核心进展
[1-2句话概括本周最重要的进展和阶段判断。这是管理者最先看的部分。]

### 产品结果
- **服务对象/场景**：[谁会使用，解决什么问题]
- **当前状态**：已上线 / 测试中 / 灰度 / POC / 阻塞
- **距离下一里程碑**：[还差什么，预计何时完成]

### 具体工作
1. **[工作项名称]**：[进展描述 + 业务意义 + 数据]
   - 关联 Feature：[Feature名]
   - 当前进度：[X%]
   - 下一步：[计划]

2. **[工作项名称]**：[进展描述 + 业务意义 + 数据]
   - 关联 Feature：[Feature名]
   - 当前进度：[X%]
   - 下一步：[计划]

### 风险与阻塞
- [如有] [风险描述 + 影响范围 + 建议应对方案]

### 下周计划
- [1-3项下周重点目标]
```

### 简化格式（工作内容较少时）

```markdown
## @[你的名字] - [日期]

**本周核心进展**：[一句话概括]

**具体工作**：
1. [工作项]：[进展 + 业务意义 + 数据]
2. [工作项]：[进展 + 业务意义 + 数据]

**风险**：[如有]

**下周计划**：[1-3项]
```

## 常见问题

### Q: 我是实习生，需要写得多详细？

实习生周报的展示方式是将贡献归入项目 Milestone，不单独列出技术进展章节。但这不意味着可以写得简略——**你的周报是管理者了解项目进展的重要信息来源**。

建议：写清楚你做的工作关联到哪个 Feature，对 Milestone 的贡献是什么。

### Q: 技术细节可以写多少？

可以写，但必须遵循"1:3原则"——**1份技术细节配3份业务翻译**。

```
❌ "GRPO跑通22步，修复了Reward传播/GRPO分组/空响应套利/CUDA Graph清理"
（纯技术，没有业务翻译）

✅ "AgenticRL训练链路工程化贯通，模型自我进化能力初步验证。
    技术：GRPO跑通22步验证Reward有效，底层环境问题已清理（Reward传播/GRPO分组/空响应/CUDA Graph）。
    业务：距业务可用约1-2个月，当前处于工程验证阶段。"
（技术细节保留，但配了业务翻译和阶段判断）
```

### Q: 如果本周没有明显进展怎么办？

诚实说明，不要凑内容：

```
✅ "本周主要在进行[工作]，暂无阶段性成果，预计[X时间]可以产出[具体成果]。
     存在[风险/阻塞]，可能影响预期。"
```

不要把日常工作包装成"进展"。"参加了3个会议"不是进展。

### Q: 周报应该写多长？

- **核心进展**：1-2句话（必填）
- **具体工作**：每项2-3句话（建议3-5项）
- **风险**：1-2条（如有）
- **下周计划**：1-3项

总字数：300-600字；具体工作最多3项。不要写流水账，不要把日报拼接成周报。

### Q: 空提交可以吗？

不可以。即使本周工作量较少，也应该提交一份简短周报说明情况。空提交会让管理者无法判断你的工作状态，增加沟通成本。

如果确实没有进展：
```markdown
## @[你的名字] - [日期]

**本周状态**：[说明原因，如"本周主要精力在[X]，预计[X]产出成果"]
**下周计划**：[1-3项]
```

## 自查清单

提交周报前，检查以下事项：

- [ ] **核心进展**是否用1-2句话概括了本周最重要的进展？
- [ ] **业务关联**：每项工作是否说明了关联到哪个 Feature？
- [ ] **业务翻译**：技术细节是否附带了业务意义说明？
- [ ] **数据具体**：是否有具体的数字和指标？
- [ ] **风险暴露**：是否主动暴露了问题和风险？
- [ ] **下一步**：是否说明了下一步计划和预期？
- [ ] **篇幅控制**：是否在300-600字以内？
- [ ] **没有流水账**：是否避免了把日报拼接成周报？
