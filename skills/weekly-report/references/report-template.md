# 周报输出模板

本文件是 weekly-report skill 的输出格式参考。使用时应根据实际项目内容填充，不要机械套用。

## 使用说明

- 本模板定义了 L0-L6 七个层层的职责和格式
- 各层级的核心问题是"回答什么"，不是"写什么"
- L1/L2/L3 之间信息重叠率必须低于 30%
- 技术指标必须翻译成管理者能理解的语言
- 管理者观点（Type C 提问收集）是 L1 的灵魂
- 主报告服务产品决策：先写目标、结果、状态和风险，再写技术证据
- L0-L4 必须让非技术读者独立读懂；L3 只保留能改变决策的技术证据
- L5 点评建议放在报告末尾折叠区，不干扰主报告阅读

---

## L0 执行摘要

```markdown
## 执行摘要

**周期**：2026年X月第X周（XX/XX-XX/XX）
**团队状态**：X人提交 / X人应提交（简要说明异常）
**本周关键词**：关键词1、关键词2、关键词3、关键词4、关键词5

### 核心进展
1. **[最重要进展]** — @负责人
2. **[次重要进展]** — @负责人
3. **[第三重要进展]** — @负责人

### 关键风险
- ⚠️ [风险描述] — @相关成员

### 决策事项
- [需要老板决策的事项，如有]
```

**要求**：200字以内。提炼自 L1，不是额外信息。

**产品可读性检查**：只看 L0，读者必须知道哪个产品前进了、什么时候能用、最大风险是什么、需要什么决策。

## L1 本周聚焦

这是报告的核心章节。不是项目进展的缩写，而是管理者的战略叙事。开篇即判断，让老板第一眼看到管理者的视角。

```markdown
## 本周聚焦

[管理者开篇叙事：2-3句战略判断，不标注"管理者判断"。用判断性语言框定本周核心变化、意义和决策需求。同时覆盖业务和技术维度。]

**[子产品名]进展描述**：一句话说清楚进展和阶段。
- **业务价值**：对业务目标的贡献。
- **待突破/风险**：下一步或风险。

**[子产品名]进展描述**：一句话说清楚进展和阶段。
- **业务价值**：对业务目标的贡献。
- **待突破/风险**：下一步或风险。

**全局风险**：⚠️ [本周需要老板关注的风险汇总]
```

### L1 写作要点

1. **开篇叙事是灵魂**：不标注"管理者判断"，直接以判断性语言开篇。内容来自 Step 2 Type C 讨论中收集的管理者观点
2. **开篇叙事要求**：2-3句话，不超过150字，用判断性语言（"本周标志着…""…的转折点""关键风险在…"）
3. **每条必须有子产品关联**：不能是孤立的动作描述
4. **必须说"现在到哪了、意味着什么"**：不说"做了什么"
5. **技术指标必须翻译**：不出现 "ED 0.078"、"SFT Loss"、"Recall@10" 等纯技术术语
6. **双线汇报**：开篇叙事和进展条目同时覆盖业务和技术维度
7. **3-5条进展**：不超过5条，聚焦最重要的

### 开篇叙事示例

```
✅ "本周翻译630验收以96.64%超额达成年度目标，标志着翻译项目从技术攻坚正式转入业务交付阶段。智能体方向'数据飞轮'闭环初具雏形，但下半年三方向均有人员缺口，优先级安排是急需明确的决策事项。"

✅ "本周Core Runtime通过ACP协议打通下游，智能体研发效率将大幅提升，为630攻坚提供基础保障。但Rebuttal集成存在延迟风险，需通过MVP版本验证基线。"
```

### 技术指标翻译示例

| 原始 | 翻译后 |
|------|--------|
| "SFT Loss 2.946→0.878" | "模型自我进化能力初步验证，距业务可用约1-2个月" |
| "ED 0.078（目标<0.1）" | "文档还原精度达标，低成本方案可行性验证通过" |
| "Recall@10 0.6667 vs 0.2292" | "结构化检索准确率提升近3倍，验证方案有效" |
| "F1 0.9488" | "跨页表格识别能力达到可用水平" |
| "问答准确率 65.25%" | "文档问答能力持续提升，距70%目标还有差距" |

### 好 vs 坏

```
❌ "完成Agent Pool迁移"（动作描述，没有子产品关联）
❌ "DeepSeek OCR-2 ED<0.1"（纯技术指标，老板看不懂）
❌ "术语库2.0版本，121万条概念"（数字罗列，没有阶段判断）
❌ "**管理者判断**：本周..."（不应有标签，直接以判断开篇）

✅ "【感知压缩】单页场景达标，低成本方案可行性得到验证，为Q3-Q4产品化奠定基础"
✅ "【术语库建设】核心概念覆盖完成，进入质量优化阶段"
✅ "【AgentOS】架构层就绪，支撑630诊断通过率目标"
```

字数控制: 300字

**产品化写法**：每条按“目标 → 当前结果 → 用户价值 → 状态/差距”组织；不要从技术动作开头。

## L2 项目进展

按项目集→子产品→阶段目标组织，回答业务老板的核心问题："产品到哪了？什么时候能用？"

```markdown
## 项目进展

### 『项目集名』@负责人

#### 子产品名 — 阶段：[POC/MVP/私有化部署]

> 新规范：阶段统一使用 **POC / Pilot / Production**；三一和SaaS另列为验证场景、部署形态。

**Milestone 对齐**：
| Milestone | 目标 | 当前进度 | 本周推进 | on track? | 负责人 |
|-----------|------|---------|---------|-----------|--------|
| [里程碑名] | [目标] | [X%] | [本周推进了什么] | ✅/⚠️/🔴 | @... |
| [里程碑名] | [目标] | [X%] | [本周推进了什么] | ✅/⚠️/🔴 | @... |

**本周进展**：
- **里程碑名（进度）**：进展描述（翻译后的管理者视角）@负责人

**阻塞/风险**：
- ⚠️ [风险描述及影响] @相关成员

**下一步**：预计何时进入下一阶段

**责任边界**：算法负责[POC/试用中的能力验证]；产品/工程负责[用户组织、版本、SLA、监控和生产部署]。

#### 另一个子产品名 — 阶段：[POC/MVP/私有化部署]
...
```

### L2 写作要点

1. **按项目集→子产品组织**：维修助手下有维修诊断智能体、专家访谈智能体、对话自迭代反馈闭环、Agent DB；翻译助手下有术语、翻译、QA质检
2. **每个子产品必须标注阶段**：POC（演示验证）/ MVP（上线SaaS）/ 私有化部署（三一）
3. **Milestone 对齐表是核心**：一目了然看到 on track 状态
4. **进展描述是翻译后的**：不是下属原文，技术细节已翻译
5. **风险标注分级**：🔴重大风险 / ⚠️一般风险 / 💡提示
6. **实习生贡献归入 Milestone**：不单独列出
7. **多模态不是独立项目**：其工作映射到服务的子产品中

### 项目集与子产品参考

**维修助手项目集**：
- 维修诊断智能体（AgentOS/Skill化/Rebuttal/Core Runtime/NG版本）
- 专家访谈智能体（Expert Interview/专家知识沉淀）
- 对话自迭代反馈闭环（AgenticRL/Reflect/MemPalace/SKILL自迭代）
- Agent DB（知识库/自动入库归档/信息处理/检查校验/冲突检测）

**翻译助手项目集**：
- 术语（术语库/术语API/术语工程化/术语规则）
- 翻译（翻译链路/Agentic翻译/DCP/多语言扩展/XLIFF）
- QA质检（QA打分模型/六维度评估/质量闭环）

字数控制: 500字

**默认限制**：每个子产品最多保留2个关键里程碑；常规开发、会议和重复技术细节移入 Draft。

## L3 技术进展

只收录有突破的技术进展，不收录常规工作。每项工作必须关联到具体子产品/Feature，体现双线汇报中技术线对业务线的支撑。

```markdown
## 技术进展

### 【技术方向名】

#### @[正式员工姓名]
**关联子产品**：[子产品名] — [Feature名]
**技术突破**：[突破了什么技术壁垒]
**对Feature的意义**：[解决了什么问题/突破了什么阻塞/验证了什么假设]
**关键数据**：[技术指标及阶段判断依据，翻译后]
**下一步**：[计划及对Feature的贡献预期]
```

### L3 写作要点

1. **关联子产品是必填字段**：如果无法关联到任何子产品，说明这项工作的业务定位有问题
2. **只收录有突破的进展**：常规开发不列入
3. **技术指标保留但必须附带业务翻译**
4. **先说明子产品当前阶段**，再说明技术进展的推动作用
5. **下一步必须说明对子产品/Feature 的贡献预期**
6. **双线汇报**：L3 回答技术问题（壁垒在哪），但必须反向链接到 L2 子产品（服务什么业务）

### 技术指标翻译规则

| 原始 | 翻译后 |
|------|--------|
| "SFT Loss从2.946降至0.878" | "模型自我进化能力初步验证（Loss降低70%），距业务可用约1-2个月" |
| "ED 0.078" | "文档还原精度达标（目标<0.1），低成本方案可行性验证通过" |
| "Recall@10 0.6667 vs 0.2292" | "结构化检索准确率提升近3倍，验证方案有效" |

字数控制: 500字

**准入标准**：只有满足“突破技术瓶颈、改变上线判断、显著降低成本/风险”之一的技术进展才进入 L3。每项最多保留一个关键数据和一个下一步动作。

## L4 排兵布阵

不是人力列表，而是资源分配的论证。

```markdown
## 排兵布阵

### 当前人力分配
| 方向 | 人员 | FTE | KR 进度 | 投入产出评估 |
|------|------|-----|---------|-------------|
| [方向名] | @人员 | [X] | [X%] | [评估] |
| [方向名] | @人员 | [X] | [X%] | [评估] |

### 分配逻辑
- [每个方向的分配理由和取舍说明]

### 需要关注
- [人力缺口、优先级冲突、需要调整的地方]

### 人力变动
- [本周入职/离职/转岗情况]
```

### L4 写作要点

1. **投入产出评估基于 KR 进度**：不是主观感受
2. **分配逻辑说清楚"为什么"和"放弃了什么"**
3. **需要关注的部分开放性提出调整可能**

字数控制: 100字

---

## L5 下属周报点评

用户可以直接复制粘贴给下属的反馈。

建议使用 `<details>` 折叠，避免点评内容淹没产品主线。空提交可合并点评，但必须明确责任人和下周补交要求。

```markdown
## 下属周报点评

### @[成员名]

**优点**：
- [具体优点，引用周报原文]

**改进建议**：
- [具体问题] → [改进方向]
- 示范写法："[原文]" → "[改进后写法]"
```

### L5 写作要点

1. **每人 100-200 字**
2. **必须包含优点 + 改进建议 + 示范写法**
3. **语气建设性，不指责**
4. **空提交的成员也要给出反馈**

---

## L6 下周计划

```markdown
## 下周计划

### 项目名
- **P0** | 重点目标
- **P1** | 其他目标
- **风险** | 需要关注的风险

### 项目名
- **P0** | 重点目标
- **P1** | 其他目标
- **风险** | 需要关注的风险
```

字数控制: 200-300字

**计划准入标准**：每项计划必须对应一个产品里程碑，并写明交付物或验收条件；“继续优化”“持续跟进”不能单独作为计划。

---

## 完整报告字数控制

| 章节 | 字数 |
|------|------|
| L0 执行摘要 | ≤200字 |
| L1 本周聚焦 | 300字 |
| L2 项目进展 | 500字 |
| L3 技术进展 | 500字 |
| L4 排兵布阵 | 100字 |
| L5 下属周报点评 | 每人100-200字 |
| L6 下周计划 | 200-300字 |
| **总计** | **2000-2500字**（不含L5点评） |

超出时优先删减 L3 技术流水账和重复来源说明。
